# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code. It holds only what almost every session needs; each line points to the doc under `docs/` that owns the detail.

## What this project is

Infinitary is a local-only Electron desktop app: a calm AI first mate that routes work to the user's own LLM subscriptions (Codex, Grok, Claude Max, OpenRouter, ...). No SaaS, no hosted backend, no account system from us. Product vision, interaction model, and constraints: `.claude/skills/infinitary-design/readme.md`.

## Principles (captain; full text in `docs/principles.md`)

- **Hide the machinery (2026-08-17).** Infinitary is the most advanced agent harness, but it aggressively hides that complexity from the end user. The user interacts with just the main first mate agent and a few settings - nothing else. The fewer concepts we expose, the better. The sign-in flow and the Subscriptions tab never expose the "harness" technicality - they speak only of providers, accounts (labeled by the user), and quota; an e2e assertion enforces the wording.
- **Settings → Projects (2026-09-19)** may expose delivery, autonomy, and standing rigor (accordion with a row chevron). Setup and removal are shared by Settings and `app_change` (`project-setup`, `project-remove`); the first mate removes a project only on the captain's own words. The personal workspace's row is locked and reads "builds in place". Settings writes through the same action-catalog dispatcher as `app_change project-settings`, and a refused configure is a feed line, not a silent revert.
- **Subscriptions (2026-09-24):** Supported subscriptions are only those that run through Pi; Claude is the sole exception.
- **Knowledge replaces notes in every build, stable included (2026-10-12)**: `KnowledgeService` owns standing directions separately from personal facts; every turn receives complete applicable directions, never an older-notes fallback (`docs/knowledge.md`).
- **Knowledge is user-owned (2026-10-09)**: personal context and references the captain asks to save. Project behavior stays in code, documents and tests; investigations stay on the task record. The first mate records a personal statement on the captain's words; every crewmate has equal factual read/write access and saves sources on request, using knowledge as needed (`docs/knowledge.md`, "What belongs here").
- **Every feature works from the keyboard (2026-10-04).** A new control is reached with Tab, or the arrows inside a list, and draws the focus ring. An action a person repeats becomes a command in `KEYBOARD_COMMANDS`, so command search lists it; it gets a default key only where none clashes, and its control shows the key hint. An end-to-end journey drives it by keys (`docs/keyboard.md`, "A new feature").
- **Reuse the primitives you already have (2026-09-23).** Build a new feature by arranging existing primitives; its special knowledge belongs in instructions or in data an existing reader already consumes. A missing primitive is added generically. A guided way of working is a parent task with child tasks on the existing task graph - not its own runner, stamp, or card effect. The host never learns the feature's name.
- **Put ambiguous judgments in agent instructions (2026-09-23).** Deterministic logic is for closed, typed facts. Do not build a static parser that tries to understand natural language. The host carries what the agent declared; it does not infer the judgment by parsing the words or by guessing from structure.
- **The two documents (F4c, F6b):** `DATA-TERMS.md`, `LICENSE` (Apache-2.0 + `NOTICE`) and `CONTRIBUTING.md` (no DCO) stay UNPUBLISHED until the public beta. A change to the terms is a new version of the file, never a silent edit; counsel reviews before publication (`docs/sharing.md`).

## Design system (mandatory)

All UI work MUST follow the project skill `infinitary-design` (`.claude/skills/infinitary-design/`). It owns every visual and interaction rule: tokens, type, color, motion, components, character rendering, tone of copy. Never re-invent brand rules in code; if a rule is missing, extend the skill first, then implement. The package is offline-complete (fonts and mock runtime vendored; see its readme "Offline completeness").

- Tokens: `.claude/skills/infinitary-design/tokens/*.css` - consume these, never hardcode values they define.
- Click-through mock: serve the skill dir over HTTP, open `ui_kits/firstmate/index.html` (voice states trigger on a real right-⌥ keydown).
- User-facing words follow the vocabulary (the skill's `copy/Vocabulary.prompt.md`; code side `docs/vocabulary.md`): written for someone who has never opened a terminal. It is measured by the replay gate, never a banned-word lint. These words never reach a user surface: harness, memory, extension, plugin, preference, telemetry, analytics, Umami, sequence, step.

## The green gate and tests (`docs/testing.md`)

- **New journeys are request-only** (`docs/testing.md`, "This project's rulings on tests"): a new end-to-end journey is written only on the captain's request, and its review names the promised result, the data, the completion signal, the platform prerequisites and the shared resources (FI3-1732).
- **Weakening or deleting a test is ask-first** (`docs/testing.md`, "This project's rulings on tests"): weakening, skipping or deleting an existing test waits for the captain's approval. Otherwise the crew's default rule on tests decides which tests are written and how a failing one is repaired (`docs/delivery-rigor.md`, "The default rule on tests").
- Local gate before every push: `pnpm typecheck && pnpm check && pnpm lint:adherence`, plus the relevant existing e2e specs that cover what you changed (run a `renderer`/`application` lane spec alone with `--no-deps`, or it runs the whole serial `desktop` lane). The full unit suite (`pnpm test`) runs across `ci.yml`'s PR checks on every PR, its probes only where the change reaches them; the full e2e suite runs in `verify.yml`'s mac and `linux-e2e` lanes and `pnpm package:mac` in its mac lane (every alpha, and on demand), and the affected journey files run on each PR. The full e2e suite runs only in CI, never locally during development or release preparation; request it through `github_write` as described in `docs/forge.md` ("Verification workflow requests"). The full unit suite is not a per-push obligation.
- The PR checks are `ci.yml`'s five Linux jobs, run side by side: `typecheck-lint-build`, `unit-tests`, the two `integration-tests` shards and `probe-tests`, which runs only the probes whose paths the change edits (`scripts/affected-probes.ts`, `docs/test-cohorts.md` "Probes"); `verify.yml`'s `linux-checks` lane runs the same commands with every probe (`docs/testing.md`). A pull request also gets `journeys.yml`'s `affected-journeys` on the Mac mini: only the journey files its diff can break (`scripts/affected-journeys.ts`, `docs/testing.md` "Journeys on the pull request"). CI green means every check on the exact head SHA is completed/success or completed/skipped; never treat an old SHA as authoritative for the current head.
- **A new e2e test reads frames, keys, saved data and words through their owners** (`docs/e2e-contracts.md`): a frame through `tests/e2e/frames.ts` (`cardBody`, `panelBody`, `bodyIn`), focus through `focusOn` and `pressKey`, saved data after a launch through `readSavedData`, the words it expects from the module that owns them ("Words come from their owner"); four lints in `pnpm check` refuse the raw forms.
- **Each test owns its prerequisites** (`docs/testing.md`): a named test must work alone from fresh state. An intentionally ordered journey is one test with named sections, never separate tests borrowing a predecessor's state.
- **Pictures of a visible change** (`docs/testing.md` "Capturing pictures of a change", `docs/card-authoring.md`): photograph each changed view before the first edit and again after it, through the hermetic launcher; the merge card's Before and After show them, as many as the change needs. Behavior a still cannot show gets a demo recording instead (`startDemo`, `docs/testing.md` "Recording a demo").
- A timing claim in a test is an ORDER or WORK, never a wall-clock window (captain's B1: "one clock, budgets measured"). Budgets go through `tests/e2e/perf.ts`; a lint refuses `toBeLessThan(X_MS)` elsewhere in `tests/e2e`.
- Temp directories only through `scratchDir(prefix)` (`tests/helpers/scratchDirs.ts`), never at module scope or in a Playwright `describe` body; await work that writes after a test returns. Leftovers fail the run.
- Vitest cohorts (captain's A1; `docs/test-cohorts.md`): `pure`, `unit` (in memory, 5 s default) and `integration`, whose files that can fail with no code change run as `probe`. A test that spawns must be listed as integration with a measured budget; never raise a unit test's timeout instead.
- E2E is hermetic and windowless (`tests/e2e/launch.ts`, `docs/e2e-contracts.md`): throwaway userData and HOME, `PI_OFFLINE=1`, a mock provider and a mock Claude client. Never let a test or probe start a real Claude sign-in - it reaches the captain's browser (`docs/claude-client.md`). On macOS a test pins the app's home with `CFFIXED_USER_HOME` and never boots into the real folders.
- Seed task rows through `seedTask`, never raw SQL. A migration test that reverses a column a published view reads must `dropViews` first.
- A PR touching the prompt, card lint, the whose-turn sort, routing, the first mate agent, or `src/renderer/src/cards/` runs `pnpm replay:gate` locally before pushing; the baseline moves only in a PR that explains every moved number (`docs/replay-harness.md`).

## Fences and one-writer seams

- `src/core/` imports no Electron and never reaches into `src/main/` (Biome-fenced; `docs/architecture.md` §17). New IPC channels in `src/shared/ipc.ts` carry a `surface`, and a core one its `reach` (whether a paired view, or only a computer that runs work, may ask it, `docs/connection.md`); `PROTOCOL_VERSION` rides the healthcheck. Every core shape is published in `docs/contract.json` under the version rule (`docs/contract.md`): regenerate it with `pnpm generate:contract` in the same PR, and keep a core shape expressible as JSON Schema (no `z.custom` or transform).
- Every Pi touchpoint stays behind `src/core/pi/`; never read `~/.pi`. Every `@anthropic-ai/*` import stays behind `src/core/claude/`. Forge providers are fenced to `src/core/forge/index.ts`; Jev to `src/core/decisions/`.
- Every `ModelRuntime` comes from `src/core/pi/modelRuntime.ts`, never `ModelRuntime.create` directly (`docs/model-lists.md`).
- Every model session comes from a `SessionFactory`; roles are presets (`src/core/session/`, `docs/architecture.md` §2).
- Every child process gets its environment from `hostEnv()` (`src/core/hostEnv.ts`); never spawn with `process.env` or re-ask the shell per spawn. Heavy children go through `atUtilityQos`.
- Never spawn a path inside app.asar (`docs/claude-client.md`).
- One writer each: `TaskService` over the task tables (`docs/task-record.md`); `CardService` over the card stack and its threads (`CardStore` beneath); `src/core/storage/views.ts` over view SQL; `SharingService` over sharing; `ShellPreferencesService` over appearance/layout/panels; `DevicePairing` over `userData/devices/` (`docs/devices.md`); `WebSignIns` over `userData/web-sign-ins/`, reached only through `TaskBrowsers` (`docs/task-browser.md`, "Saved sign-ins"); `KnowledgeService` over `userData/knowledge/` (`docs/knowledge.md`); `JoinedHome` over `userData/joined/` (`docs/view.md`) and over `userData/work/` when the app runs work (`docs/helper.md`), with `PlacedTasks` over its `tasks/`, `HomeRoute` over its `route.json`, `WorkingCopies` over its clones and working copies, that computer's own `AccountVault` over its `accounts/` and its own `ForgeSignIns` over its `forges/`; `PlacedSessions` over `crewmates/<task>/placed/` at the home, reaching a computer only through `WorkDevices`; feed lines only via the `broadcastEvent` seam; `AccountBackend.renew` is the one renewer - never add a second.
- Pinned twice, update both deliberately: the `window.infinitary` API (`phase0-guardrails.spec.ts`) and the first mate tool set (`FIRSTMATE_TOOLS` in `src/core/session/tools.ts`, read by `scripts/generate-self-source.mjs`, + its test).
- Sharp edges already paid for (full list in `docs/architecture.md`): Pi's `tools` allowlist gates custom tools too (name them or they silently vanish); Pi `prompt()` images ride `PromptOptions.images`, never a content array; `protocol.registerSchemesAsPrivileged` runs once per process, so the window's schemes go through `src/main/schemes.ts` and the work mode registers the frame scheme alone when its module loads (`src/main/work.ts`); Chromium drops native clicks into a hidden window's sandboxed frames, so e2e dispatches in-frame clicks; retiring a worktree never happens on the settle path.
- Presentation preferences live in the core (`src/shared/preferences.ts`), never in `localStorage` or the shell store alone.

## Credentials, quota and accounts

- Infinitary never reads a provider token; sign-ins live in per-account stores owned by `AccountVault`. The first mate flagship rebinds only at attachment points, never mid-turn (`docs/architecture.md` §16).
- Quota honesty (`docs/quota.md`): unknown is never zero; only a 401 (never a 403) triggers renewal; `auth_required` ("sign in again") only from proof - a lapsed refresh token or a 401 that survived a real renewal. A no-window fallback is never a success. An unreadable store is `unknown`, never a sign-out.
- `src/shared/quotaSignals.ts` is the one home of quota math (clean-room to quota-axi semantics; never depend on or copy quota-axi). "Ahead" is the warn state.
- The Claude client is the one the person installed (F14: "assume / require the user has already installed claude code cli"); the app ships and downloads none (`docs/claude-client.md`). A rule that must reach a Claude crewmate or the first mate on Claude lives in a tool description under 2,048 chars or a top-level parameter, never only a nested one.
- The app never runs `gh` or reads another program's sign-in; forge work goes through the forge seam and the app's own sign-in (`docs/forge.md`).
- Reading a project's pull request history: a `/pulls` page overruns `github_read`'s 256 KiB answer, so list `/issues` (it carries pull requests) and follow each answer's `nextPath`, a `/repositories/{id}/...` path; for file-level work, fetch `refs/pull/<n>/head` and replay in git (`docs/forge.md`, "Reading a project's pull request history").
- Routing (`docs/routing.md`): the tier is computed from the work's shape, never judged; premium is never auto-picked; never quiet the `routing_decisions` / `account_decisions` observability.

## The first mate, crew and cards

- The orchestrator contract (`docs/orchestrator-contract.md`): the first mate holds typed tools only - no bash, no file reads; reading is a crewmate's job. A redline is a contract revision: add one file to `src/core/prompts/contract-revisions/` (its README says how); `FIRSTMATE_CONTRACT_VERSION` counts them and is never written by hand. The card contract has one home per kind (`CARD_AUTHORING`, `CARD_MECHANICS`, `CARD_REPLY`, and `HANDOFF` for what a choice authorizes); no persona prompt repeats it.
- Crewmate isolation is social (system prompt + git worktree), not a filesystem jail; the first mate's turns are steer-only. Both are captain KEEP calls (`docs/architecture.md` §2, §4).
- Card rule (product; `docs/card-authoring.md`): a card only when work cannot move forward without a captain decision, or the captain cannot move forward without seeing that fact. Never progress, CI-wait or status cards - those are feed lines. The host's one card about work is the idle ladder's stall card, after two ignored wakes (captain, 2026-09-26; `docs/report-sort.md`). Card bodies render verbatim with no sanitizer; never reintroduce a tag/attribute/CSS allowlist. Only the captain's click on host chrome runs an effect. The card lint asks for shape, never a banned-phrase list.
- Cards are threads (`docs/card-threads.md`): a reply goes to the card's author and resolves nothing, and the captain's close of a crewmate's card reaches that crewmate, which judges it; nothing in the host reads the captain's words.
- Answer delivery (`docs/task-capture.md`): each captain message is checked for one action that took effect after the first mate read it - never for whether the answer is right. One output-only retry (the typed `answer-missing` wake, mutation tools refused), then one task-less notice (`card-ask-<id>`, Ask again or Leave it); the saved state lives on `captain_asks`, and closing words are never a card.
- Whose turn (`docs/report-sort.md`, captain's C7 A "heuristics only"): a report is sorted in code from typed state, never by reading its prose; every idle crewmate, whatever left it idle, is read by one reconciler on a durable clock (the idle ladder), whose only trigger is a missing witness, never a named situation. The sort and the ladder read one witness set (`IdleLadder.witnesses`), and the gate is a witness: every card with actions, and a wait on the captain a crewmate declares in its report, places the `captain` gate on its task (a task-less host card files an `operation` row), a round cap is that gate, never a second wait (`docs/task-graph.md`). Every steer and wake rides the durable inbox (`docs/inbox.md`); a wake carries new information or it does not fire, and a provider failure spends no delivery attempt (the honest retry).
- A provider-failed turn must stay a `turn_failed` event; auth classification lives only in `src/shared/authFailure.ts`, never substring matching. The first mate's turn ends with brief output - never empty, never the exact token `done` (`docs/firstmate-runaway-hardening.md`).
- Fleet management is agent-operated (`docs/fleet.md`): Settings may add and remove projects through `app_change`'s dispatcher (`project-setup`, `project-remove`); removal never deletes repo data. The host enforces autonomy on merges.
- A task is a record, never a handle (`docs/task-record.md`). A done/dropped close always retires the worktree and branch (captain: "cleaned up period. no exceptions"), saving unlanded work to `refs/infinitary/kept/<task-id>` first. Sessions are durable and nothing prunes them (captain: "we shouldn't remove the entire session JSONL altogether"). A graph refusal is tool text, never a thrown error or a silent no-op (`docs/task-graph.md`).
- Sequences are guidance, never a runner; never add a host rule that knows the word "sequence" (`docs/sequences.md`).

Commit subjects and pull request titles use `type(scope): summary` or `type: summary` (optional `!` and `BREAKING CHANGE` footer). Use `feat`, `fix`, `chore`, `test`, `refactor`, `docs`, or `perf`; scopes are open-ended (for example `cards`, `crew`, `e2e`, `main`). `feat`, `fix`, and breaking changes drive release versions; never mislabel a fix as a feature. The host checks new subjects and pull request titles before opening or merging and squashes GitHub pull requests using the checked title.

## Delivery (`docs/delivery-rigor.md`)

- Delivery direct-pr (captain rule): a crewmate that opens a PR babysits CI until every check on the head SHA is green before its final report; the first mate never presents a land/merge/accept decision while CI is red or running.
- Rigor tiers quick / standard / reviewed; standard is every repository's default, and a task with no gate to land through takes no tier. Reports and PR bodies carry five headings in order: Intent, What changed, Verified, Risk, Not done. Failed checks are diagnosed first; three unsuccessful own repairs exhaust the allowance, while evidenced baseline waits and one reserved flake rerun spend nothing (`docs/delivery-rigor.md`).

## Build, packaging and state

- Where state lives (captain, 2026-09-22): the release uses `<appData>/infinitary`, every other run `<appData>/infinitary-dev`; nothing migrates between them (`docs/architecture.md`). Each moves its Firstmate 3000 folder (`firstmate-3000`, `firstmate-3000-dev`) into itself once (`docs/saved-data-compatibility.md`, "The one-time move").
- A working copy is on the person's Mac, and a scratch HOME does not move its keychain search list (`docs/local-code-signing.md`, "In a crewmate's working copy"). Never package with the release `electron-builder.yml`: its identity lookup reads the real keychains and has signed with a personal certificate even with `-c.mac.identity=-`; only `-c.mac.identity=null` skips it. `pnpm dev`, `pnpm codesign:local` and `pnpm package:mac` sign with this Mac's material, so they are the person's to run. An install only checks, including the one pnpm starts on its own before a script after any `package.json` or lockfile change.
- `pnpm package:mac`'s fuse-flipped binary MUST be re-signed; signing stays at electron-builder's `sign` hook; release signing is Developer ID only. `mac.x64ArchFiles` is the one single-arch list (`docs/local-code-signing.md`). Release invariants: `tests/release-contract.test.ts`; alpha publishing and the two channels: `docs/alpha.md`. An alpha is cut from one release candidate, the release crewmate's notes-only review commit off main, checked once and followed by one pull request (`docs/alpha.md` "Cutting an alpha"); never wait on main's own checks. Every stable is a promoted alpha built on its alpha's own commit, with no pull request (`docs/alpha.md` "Promoting an alpha"): "promote the current alpha" starts one, and its crewmate first has the captain pick the stable's three highlights on a card. A request for "a release" that names no channel means alpha, while `release.yml`'s own default stays stable, so always pass the channel explicitly (`docs/alpha.md` "Activating the channels").
- Electron 43's tarball has no `postinstall`; `scripts/ensure-electron-installed.mjs` installs the binary from ours. Verify a future major from the tarball, not `npm view` (`docs/architecture.md`).
- Release notes (`docs/release-notes.md`): a change a person notices adds a plain-language note under `release-notes/changes/` in the same PR, or an exclusion with a reason for internal work; a missing one blocks the next alpha. A note follows "What a note may say": only changes a person notices, and no product the app does not support. The note declares its `area`, and a change a person can see commits a hero picture pair in `release-notes/pictures/` (`heroShot`, `docs/testing.md` "A hero picture"; part of the change, not evidence) or a one-sentence `noPicture` reason; `tests/release-notes-ledger.test.ts` refuses a missing one, and a new `maintenance` note, on the PR. The release crewmate reviews every note against the actual changes before an alpha and dispatches its review commit as the `candidate`; after the private tag exists, that crewmate pins the release's manifest on the same branch and never rewrites it, and the notes check refuses a published release with no record. A stable promotion never edits `release-notes/`.
- Never hand-edit generated files: `CHANGELOG.md`, `firstmateEnv.generated.ts` (`pnpm generate:personal-env`), `docs/contract.json` (`pnpm generate:contract`), self-source output.
- Offline dev tools (`scripts/*.ts`: C2/C4/C5 exporters, replay, and G1's pre-S7c supervision archive reader only) are documented in `docs/miss-deriver.md`, `docs/corpus-export.md`, `docs/dispatch-extractor.md`, `docs/supervision-extractor.md`, `docs/provenance-capture.md`.
