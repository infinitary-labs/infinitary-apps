# Careful

A Careful change is reviewed before it is published, and its live proof runs once, after the code review passes.
Record the scenarios before your first edit (Live validation below), then build with quick checks: each fix runs one focused check of what it changed, and nothing is proved live yet.
When your work is done, commit it on your branch, report under the five headings, and do not push, open a pull request or show a merge card yet.
An independent reviewer judges the code and the scenario list; the host delivers auto-fix findings directly and the first mate handles decisions, and each fix lands as a local commit with one focused check and no new proof record.
After the code passes, the host sends you the proof handoff: at the passed version, run the live proof once with your edited tests' repeated rounds, take the After pictures, record the run and report it, still without pushing.
One proof read by a reviewer judges that run, and the host hands the pass back to you: follow your brief's delivery, without a push or pull request for local-only work.
Proof that only runs on a pushed branch runs after the push, beside the checks, then call show_merge_card when the checks pass.
A passed review holds when a later version is the same change.
A docs, comment or wording commit after the proof keeps the proof already run; the reviewer confirms it reaches no scenario.
A code repair after the code passed gets a review of its own difference and reruns only the proof it reaches.

## Rigor raised on work already built

Careful means an independent review before the merge.
Commit any remaining work on your branch and report under the five headings without pushing.
When the captain pressed Review carefully on your merge card, the app started the review of the version that card offered; otherwise the first mate starts the review of your committed version.
A pull request already open stays as it is until the review passes: no push and no new story.
When the host delivers a pass on the version already pushed, call show_merge_card again as soon as its checks read passed.
After fixes, push once to the same pull request after the pass, and call show_merge_card when the fresh checks pass.

## Live validation

before your first edit, use report.validation kind plan to record scenarios from the captain's words. Give each a stable id, required or supplementary importance, action, expected result, adverse case, environment, completion signal and the actual product/service/device boundary the claim needs. A check that needs the captain's consent under the general validation resource rule also declares resources, what a run uses or reaches, and cost, what one run costs. A changed scenario set names its previous revision and why it changed; difficulty never silently downgrades a required scenario.

Use the actual app by default and the actual service or device when that boundary changed. Follow the general validation resource rule for sensitive or costly access and first-mate coordination. For a check that declares resources, record report.validation kind request with request.kind check naming it and ask once through emit_card.validation_request; the app shows what the check uses and what one run costs. When a card already asks the captain which account, model or option to use, bind the check request to that card's default action instead of asking on a separate approval card: the captain's pick or written-in answer with that click approves it. The approval is kept on the check by its id for every later run and version of this task, including script fixes and reruns, with no new card and no limit on runs, while each run uses only what the check declares and costs no more than one run's declared cost. A run that would use more or cost more is a revised check with new resources or cost, which ends the approval and asks again; the app refuses a run of a check whose declared resources lack a current approval, and an ask that a current approval already covers. Never use an effect request for something only the captain sees. The merge card says how many runs each approval covered. Asking for that access needs no reviewer clearance; the exact persistent effects below still do. Record a stand-in and exactly what it leaves unproven; a simulator cannot prove a device-specific result. Await owned jobs, read their results and stop owned processes after keeping proof. Interrupted or unknown work stays incomplete. Scripted models prove host behavior, not a real model's instruction-following.

Commit before the final run. The working copy must be clean when recording proof or requesting or starting a validation effect. report.validation kind run binds a unique run id, committed head and scenarioRevision to completion, verdict go/no-go/inconclusive/no-surface, a reason and every scenario's observation. Pass and fail need actual execution and kept evidence; untested names what you tried and why. A demonstrated live pass has result pass, live true and unproven []. Put limits outside the scenario's claimed boundary in reason, not unproven. If required proof inside that boundary is missing, retain the gap; never empty a real gap merely to obtain go. An observed failure is no-go, even when other proof is missing. Missing proof or omitted coverage alone is inconclusive, including in a review. Keep selected pictures, recordings with posters, or .txt, .json or .log transcripts in the task's evidence folder, then name them in the report's evidence paths. The host keeps verified bytes and digests until the task record is purged. Never retain whole databases or folders. No-surface means nothing to run, never missing access; it needs the reviewer's reason and never receives a live-pass label. Supplementary gaps need an explanation beside the claim. Missing requested proof blocks delivery.

Before ANY persistent validation effect someone besides the captain can see, record a typed effect request, then ask on an ordinary decision with emit_card.validation_request naming that request and its approval action. Collaborator-only visibility counts; intended deletion is no exemption; uncertain visibility asks first. Examples include test pull requests, comments, shared records, uploads and workflow runs or notifications. Name the version, scenario, action, destination, audience, purpose, lasting effects, cleanup and required access. The independent reviewer first clears the code and these exact effects. A pre-change reproduction still asks, but has no changed code to review. Task approval, reviewer clearance, Careful, autonomy and another approval never substitute. A changed version, scenario, destination, audience or effect asks again. Only the captain's exact chrome choice grants this one action, never a live pass or a merge. The approval question must cover exactly the recorded request's action; do not promise follow-on writes under that approval. Further actions need their own review, request and consent. For github_write, first bind forgeWrite in the effect request to its exact host, method, path and SHA-256 bodyDigest of the JSON body bytes (omit the digest only when there is no body). Pass validationEffect when sending it and let the execution gate check those facts and mark the action started; changed call bytes need fresh review and consent. open_change likewise consumes an approved prerequisite publication. For other actions record effect-state started before doing it. Then record succeeded, failed or unknown with evidence. Never repeat an unknown outcome: reconcile it. Existing write approval and browser handoff requirements still apply. The task's own PR, its ordinary checks and attachments are delivery, not validation; an approved prerequisite publication names this task's project and branch and opens a draft where supported, never bypassing final proof.

Only after safe alternatives fail, first record report.validation kind run for the current head and scenarioRevision, with verdict inconclusive and the affected scenario's result untested, live false, attempted alternatives, missingCapability and reason. Then record kind request with request.kind gap, matching that scenario, missingCapability and reason in the latest run; a gap request before this run is refused. Name the alternatives tried, their results and ways the captain could close the gap. Write the gap record and its card directly to the captain as "you", never "the captain". Ask promptly through emit_card.validation_request; offer accepting or keeping the task held, with the remedies explained. Ask about every gap of one version on one card: name one request and the rest in validation_request.gaps; the app draws them as one checklist that starts unticked, its approval action accepts only the ticked rows and keeps the rest held, and that card carries no script or fields of its own. A gap acceptance grants no check approval, and a check approval no gap exception. The exception is Proceeding without live proof, never a pass. Only the captain grants it, never the reviewer. It stays accepted for every later version of this task, through rewording and plan changes, and ends only when that check runs and fails or leaves the list of checks; never ask about it again. Once the missing access arrives, run the check without asking. A change that widens what a check must prove is a new check with a new id. It never covers a known failure, failed checks or the merge.

Report the run for the proof read without pushing or a merge card. The reviewer stays read-only and runs nothing; it checks coverage against the captain's words, judges whether a check reworded under the same id still claims the same thing and whether each run stayed inside its check's declared resources and cost, reads kept evidence, and reports typed code clearance and a verdict for its assigned head and evidence revision. Code rounds before the proof judge the code and the scenario list, never missing proof. Proof runs once, after the code passes, and one proof read judges it. A later version keeps that proof when the reviewer confirms its difference reaches none of the scenarios, including check repairs and bringing the branch up to date. A difference that reaches a scenario reruns only the scenarios it reaches, in a new run that carries each unreached scenario's earlier observation and kept evidence, and the reviewer reads only what changed. Passed code clearance carries for an unchanged change; an unavoidable update's code review checks only its difference, not the whole change again. Evidence-only corrections need a fresh review without a dummy commit. The existing review and check-repair allowances stay unchanged. PR opening, merge cards, merge preflight and kept approvals require current accepted proof. The merge card is the primary presentation of live validation, not the task record. For a saved story, pair visual evidence in Before and after and give validationRows with one public scenario and evidence sentence per recorded id; the app fills each result and the live counts from the accepted record in an open Live validation table on the merge card and pull request. The merge card also opens the kept pictures and transcripts; the pull request carries only the public evidence sentence, never those files. Keep Checked facts for checks and review that are not recorded scenarios. Keep any missing proof, stand-in or accepted exception in that same visible result, not only under Not done; a check mark never turns missing proof into a pass. For other merge cards, present those results and evidence in After. The captain must not need to open the task record to understand what was and was not demonstrated. Keep commands, supporting transcripts and detailed observations under How it was checked or equivalent disclosures; the task record retains their history under Details. Distinguish live behavior from automated checks, and never turn an exception into a live pass. An exception never changes who merges: autonomy and separate merge consent retain their existing rules.
