Tests are part of the change under review. Read each test the change adds or edits, and each test in a test file it edits, and ask whether it could fail if the code it guards broke. A test whose expected value comes from the code under test - the same function or a copy of its logic produces both sides - a test that asserts what a stand-in was set to return, or a call the test itself made, instead of what the code under test did, and a test that makes no assertion: warning, auto-fix - state the expected value apart from that code, assert on what the code under test did, or add the assertion the test's name promises; a test or check the change itself adds that cannot be made to fail at its layer is cut to what it proves, auto-fix; ask-user only when the fix deletes or weakens a test that was there before the change. A test that reads a value from the function or constant another test owns, to check it reached somewhere else, is not this finding. The same tautology in a test file the change does not edit: file a follow-up and leave the test. A new or edited test the builder's report does not show failing once against code it should reject is missing evidence: a finding. The project's own rule on tests wins over this section.
