# The team queue is removed

The last piece of the captain's approved plan for batches of their own: the app no longer ships or reads a queue workflow in a project, so every batched project on a host that takes a batch pull request combines the captain's approved changes into batches of their own.
The `queue-plan-asked`, `queue-offered`, `queue-paused` and `queue-stalled` wakes are gone, with the rules each owned: nothing asks the first mate to plan, update, repair or start a project's queue.
A wake of one of those kinds saved before the update is served once as data this version cannot word, and asks for nothing.
The `app_change` catalog drops `project-queue-answer`; `project-batch-answer` is the one answer to a held batch, and the fixed context shrinks by its line, about 50 tokens.
The new `team-queue-left` wake owns the one rule this piece adds: a project still carries the files of the team queue an earlier version shipped, so the first mate offers once, on one decision card, a task in that project that removes them with a pull request.
The wake names the files it found on the default branch and, where a rule of that branch still requires the queue's status, that rule in the host's own name for it, for the card and the task's brief to name.
Not now leaves the files where they are, and the app tells each project's files once.
The wake costs about 150 tokens when it fires, and about 60 more when it names a rule.
A crewmate's `check_change` keeps the `answered` verdict for one use, the host's own merge queue removing a version without merging it; it no longer answers a team queue's send-back, and the app refuses an answer where that queue removed nothing.
The delivery guidance's sentence about a failed batch check now says a new version joins the next batch once approved.
The runbook that carries the batch-repair skill is `batches`; the queue-setup and queue-repair skills are gone.
